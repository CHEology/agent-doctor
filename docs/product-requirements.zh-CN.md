## 1. 摘要

Agent Doctor 是一款本地运行、Codex-first 的诊断产品，面向使用或编写多个
Agent Skills 和指令文件的用户。它帮助用户发现：单独看起来合理的配置，组合后
是否产生歧义、重复、矛盾、触发范围过宽或上下文浪费。

产品默认只读。只有用户提前授予边界明确的权限，或者在写入前明确确认具体变更集，
Agent Doctor 才能应用修复。所有受支持的写入必须可审阅、可归因、可验证、可回退。

MVP 优先保证判断准确、证据清楚，而不是追求最大覆盖率。证据不足时，产品应明确
输出“证据不足”，不能为了给出答案而制造确定性。

## 2. 问题与机会

当用户安装越来越多 Skills，并同时使用全局、仓库级和目录级指令时，配置质量不再
只是单个文件自身的属性。多个安全、正常的组件组合后仍可能出现问题：

- 两个 Skills 争抢同一类请求；
- 两条指令要求执行互不兼容的动作或输出格式；
- Skill 声明的触发范围明显大于实际用途；
- 覆盖文件悄然改变某个目录实际适用的指令；
- 失效引用、重复内容或过长描述造成噪声和上下文浪费；
- 用户无法分清某个冲突是静态证据已经证明的事实，还是对运行时行为的推测。

现有安全扫描器主要判断 Skill 是否恶意或不安全。Agent Doctor 关注的是另一类问题：
一组原本正当的 Agent 配置能否协调工作，以及每个修复建议是否有可追溯证据。

## 3. 产品愿景

让高级 Agent 用户能够可靠回答以下问题：

1. 当前工作区实际有哪些 Agent 配置？
2. 哪些内容发生了重叠、冲突、覆盖、重复或失效？
3. 每个结论的证据是什么？
4. 应该修改什么，可能带来什么影响？
5. 如果授权产品修复，能否先审阅并在需要时安全撤销？

产品保留较宽的 `Agent Doctor` 品牌，以便未来扩展到其他 Agent 系统；MVP 明确只做
Codex-first。

## 4. 目标

### 4.1 MVP 目标

- 盘点选定工作区相关的 Codex Skills、`AGENTS.md` 指令链和相关配置输入；
- 无需云端模型即可发现高置信度的确定性问题；
- 用户启用模型分析后，发现并解释语义重叠与语义冲突；
- 在报告中明确区分事实、推断和未知；
- 输出可用的终端、Markdown、JSON 和 CI 结果；
- 默认只提供边界明确的修复建议，不修改文件；
- 仅在有效授权下应用精确且可审阅的变更集；
- 对产品声称支持的每种写入提供可靠回退；
- 遵循数据最小化原则，明确披露将发送给模型提供商的内容。

### 4.2 长期目标

- 引入运行时证据，用来验证或否定静态分析产生的假设；
- 支持团队治理和政策基线；
- 在 Codex-first 模型得到验证后，扩展到其他 Agent 生态。

## 5. 非目标

MVP 不会：

- 保证模型面对每一个未来提示时一定选择哪个 Skill；
- 只有静态证据时却宣称已经证明运行时因果关系；
- 替代恶意软件、提示注入、依赖或供应链安全扫描器；
- 未经边界明确的预授权或具体变更确认就自动修改文件；
- 提供不受限制的自主维护模式；
- 同时支持 Claude Code、Gemini CLI 和所有 Agent 框架；
- 提供托管 SaaS 仪表盘、组织管理后台或计费系统；
- 提供桌面 GUI 或 IDE-first 体验；
- 优化通用提示词或改写任意项目文档；
- 在本 PRD 中决定最终实现架构。

## 6. 目标用户

### 6.1 主要用户：高级个人 Agent 用户

这类开发者或知识工作者安装了较多 Skills，同时使用全局和项目级指令，需要理解
自己的配置为什么变得不可预测、冗余或臃肿。

核心需求：

- 快速获得本地配置实际生效情况的解释；
- 确信诊断过程不会擅自修改配置；
- 获得足够精确的证据，以便手动修复；
- 在愿意授权时，可以安全应用并撤销修复。

### 6.2 主要用户：Skill 作者或维护者

这类用户需要判断一个 Skill 是否触发范围过宽、是否与已有 Skill 重复、是否与常见
指令冲突，或者是否形成模糊的触发边界。

核心需求：

- 可在问题单和 CI 中复现的诊断结果；
- 正例、反例和边界例；
- 机器可读的结果与稳定问题标识；
- 能区分 Skill 自身缺陷和特定安装组合造成的问题。

### 6.3 次要用户：团队平台工程师

负责共享 Agent 配置的维护者。这个角色会影响报告和 CI 需求，但 MVP 不会围绕团队
管理功能展开。

## 7. 核心用户流程

### 流程 A：诊断不可预测的本地配置

1. 用户选择工作区或受支持的配置范围；
2. Agent Doctor 说明将检查哪些内容，并确认当前为只读模式；
3. 产品盘点实际生效和相关的配置来源；
4. 产品报告确定性缺陷、语义冲突候选项、证据、严重程度、置信度和后续建议；
5. 用户自行修复，或要求产品生成修复方案。

### 流程 B：审阅并应用修复建议

1. 用户选择一个或多个问题；
2. Agent Doctor 生成精确变更集、预期效果、风险、验证计划和回退可用性；
3. 产品确认以下条件之一成立：
   - 现有的边界明确预授权覆盖这些文件和操作；
   - 用户在写入前明确确认这一个具体变更集；
4. 产品只应用获批变更，并验证修改后的状态；
5. 产品记录改动内容并提供回退操作；
6. 回退时恢复先前状态，但不能覆盖用户或其他进程之后产生的无关改动。如果无法安全
   回退，产品必须停止并解释冲突。

### 流程 C：发布 Skill 前进行验证

1. Skill 作者针对待发布 Skill 和一组有代表性的指令环境运行 Agent Doctor；
2. 报告指出过宽触发、缺少排除条件、重复、矛盾、无效引用和尚未解决的歧义；
3. CI 获得稳定的机器可读结果和退出状态；
4. 作者结合证据和后续黄金样例修订 Skill。

### 流程 D：不向模型共享内容

1. 用户关闭语义覆盖、拒绝精确披露清单，或没有可用模型提供商；
2. Agent Doctor 在本地完成全部确定性检查；
3. 报告把语义检查标为“未运行”，不能标为“通过”。

## 8. 产品原则

1. **默认只读。** 允许分析不等于允许写入。
2. **授权必须有边界。** 权限必须指定目标、操作类别以及适用会话或有效期，不能成为
   永久的笼统授权。
3. **写入前预览。** 每次写入前都展示精确变更集，包括预授权覆盖的写入。
4. **回退属于变更的一部分。** 如果无法保存先前状态并提供安全回退，该写入类型就不
   属于受支持能力。
5. **先有证据，再谈置信度。** 每个问题都引用来源，并区分观察事实和语义推断。
6. **准确率优先于覆盖率。** 允许拒绝判断。
7. **默认本地、默认最小化。** 确定性分析离线执行，外部模型可选且必须披露。
8. **不得静默扩大范围。** 发现、模型提交、修改和回退都只能发生在已展示的范围内。

## 9. 范围模型

### 9.1 MVP 输入

- Codex Skill 清单和 `SKILL.md` 内容；
- 验证问题所需、由 Skill 直接引用的资源；
- 适用于当前范围的全局、仓库级和嵌套 `AGENTS.md` 或覆盖文件；
- 会影响发现、作用域或上下文的受支持配置值；
- 用户选择的工作区和分析设置。

脚本和引用文件默认视为敏感内容。确定性检查可以查看其存在性和元数据，但除非事先向
用户展示并获得对应披露范围的授权，否则不得把内容发送给模型。

### 9.2 MVP 输出

- 人类可读的终端摘要；
- 可长期保存的 Markdown 报告；
- 带版本的 JSON 结果；
- CI 可用的退出结果；
- 可选的修复方案；
- 可选的已批准变更记录与回退记录。

### 9.3 检查状态

每项检查必须落入以下状态之一：

- `pass`：已执行该检查，未发现问题；
- `finding`：有充分证据支持问题成立；
- `candidate`：证据提示可能有问题，但需要判断或运行时验证；
- `insufficient_evidence`：产品无法负责任地作出判断；
- `not_run`：检查不可用、被关闭或超出范围；
- `error`：检查未能完成。

`not_run` 和 `insufficient_evidence` 绝不能呈现为 `pass`。

## 10. 需求与优先级

优先级定义：

- **P0：** MVP 值得信任并可发布的必要条件；
- **P1：** 公共 v0.1 足够有用的必要条件，但可以在第一个垂直切片之后完成；
- **P2：** 明确推迟到 MVP 基础得到验证之后。

### 10.1 P0：范围与盘点

- P0-R1：扫描前展示分析范围；
- P0-R2：识别与所选工作区相关、且属于受支持范围的 Skill 与指令来源；
- P0-R3：在能够确定时解释来源优先级和实际作用域；
- P0-R4：明确报告被忽略、被遮蔽、被截断、缺失或不可读的来源，不能静默省略；
- P0-R5：在长期输出中记录产品版本、规则集版本、时间、范围和启用的分析模式。

### 10.2 P0：确定性诊断

- P0-R6：发现重复标识符和结构上重复的安装；
- P0-R7：发现受支持范围内失效或越界的引用；
- P0-R8：发现必填元数据格式错误和不受支持的声明；
- P0-R9：发现能够确定的优先级、覆盖和上下文预算风险；
- P0-R10：每个确定性问题都提供来源位置、规则标识、严重程度和修复建议。

### 10.3 P0：证据与不确定性

- P0-R11：每个结论都标明属于观察、推导还是推断；
- P0-R12：提供足够的来源片段或位置，支持独立复核，同时不暴露无关秘密；
- P0-R13：明确使用候选、证据不足、未运行和错误状态；
- P0-R14：不能把模型输出本身当成确定性证据；
- P0-R15：合并实质相同的问题，并解释相关问题之间的关系。

### 10.4 P0：安全修复与回退

- P0-R16：除非明确提供边界有效的授权，每次运行都从只读模式开始；
- P0-R17：修复方案必须显示精确目标、差异、原因、预期效果、风险、验证方式和回退
  可用性；
- P0-R18：写入前必须有有效的边界预授权，或者用户对具体方案的明确确认；
- P0-R19：预授权必须受到目标范围、允许操作类别以及会话或有效期限制，并且可以撤销；
- P0-R20：即使已有预授权，写入前仍须展示变更集，不得静默扩大；
- P0-R21：写入前保存相关先前状态，并确认目标从生成方案后没有被改动；
- P0-R22：只应用获批变更；发生部分应用或冲突时，必须停止并明确报告状态；
- P0-R23：验证修改后的条件，并保存可归因的变更记录；
- P0-R24：每种受支持写入都必须提供回退；如果回退会覆盖用户之后的无关修改，必须
  拒绝回退，而不是强行覆盖；
- P0-R25：允许分析、允许模型使用或允许读取都不等于允许写入。

### 10.5 P0：隐私与模型使用

- P0-R26：不使用模型、没有网络时仍可完成确定性分析；
- P0-R27：默认启用语义覆盖和有边界的问题规划。用户显式发起“完整语义诊断”时，只授权
  紧接着生成的单次披露 manifest；每个提供商调用仍须在程序上绑定其精确 digest。
  保留 `prepare/invoke` 作为先检查后确认的高级流程；支持显式关闭、精确纳入/排除范围，
  以及用户提供的模型凭证或提供商配置；
- P0-R28：独立调用模型前，披露提供商和可能提交的精确文件/内容范围；一键运行则必须在
  启动提供商进程前，把同一 manifest、排除项、提供商/模型/推理强度、目的和 digest
  写入本地审计产物，且不得因此获得持久或后台授权；
- P0-R29：默认排除秘密、可执行脚本和无关的完整引用文件；
- P0-R30：记录哪些检查使用了模型，但不记录秘密或原始凭证；
- P0-R31：语义覆盖被关闭或提供商不可用时，相关检查标为 `not_run`；普通确定性 `scan`
  开启了语义覆盖但未运行模型 panel 时，必须报告“等待执行”，不能写成已关闭或已通过；
  用户显式要求完整诊断时，除非用户关闭、缩小或排除范围，否则应执行有边界的一键语义流程。
  精确解析范围后若不足两个 Skill，应以零提供商调用记录独立的
  `semantic_relationship_scope_not_applicable` 适用性通过项；不能把关系分析本身写成已完成，
  也不能擅自扩大范围。
- P0-R32：在相互隔离的临时上下文中并行运行两个盲审分析 Agent，二者验证通过后再启动
  第三个全新上下文的仲裁 Agent。分析者分歧即使被仲裁也必须可见，最多形成 candidate；
  只有本地确定性规则可以决定产品状态、严重程度、置信度、证据来源、分组和修复兼容性。

### 10.6 P1：语义诊断

- P1-R1：识别 Skill 触发范围重叠，并解释重叠区域与各自独有区域；
- P1-R2：识别必做动作、禁止动作、提问策略、输出约束和适用边界之间的矛盾；
- P1-R3：区分冲突、重复、互补、覆盖和不确定，不能把相似一律判为冲突；
- P1-R4：为后续评测建议正例、反例和边界例；
- P1-R5：当多文件共同造成一个交互问题时，将证据组织成一个问题，而不是重复报警；
- P1-R6：提供校准后的置信度，并解释为什么拒绝判断。

### 10.7 P1：报告与 CI

- P1-R7：由同一结果集生成终端、Markdown 和带版本的 JSON 输出；
- P1-R8：提供有文档说明的 CI 结果，区分程序执行失败和策略阈值未通过；
- P1-R9：允许配置严重程度和置信度阈值，但长期报告不能因此隐藏低级别问题；
- P1-R10：使用稳定的问题和规则标识，支持基线与问题跟踪。
- P1-R11：人工报告按已分配或潜在严重程度排列 finding 与 candidate，展示带精确
  位置的代表性来源原句，区分确定性 finding、模型推断 finding 与未确认 candidate，
  保留反例，并统计有界终端视图省略的问题或摘录。尚未提问的语义关系属于覆盖缺口，
  不能写成风险。

### 10.8 P2：推迟能力

- 收集运行时轨迹并验证因果关系；
- 从真实失败会话自动生成回归测试；
- 团队政策包与集中管理；
- 非 Codex Agent 生态适配器；
- 桌面或 IDE 原生界面；
- 无人值守的周期性修复；
- 托管协作与分析。

## 11. 严重程度与置信度

严重程度表示潜在用户影响，不表示结论有多确定：

- `critical`：可能造成破坏性或未授权行为；
- `high`：很可能选择错误流程或违反重要约束；
- `medium`：持续产生歧义、重复或结果退化；
- `low`：造成可维护性、清晰度或上下文效率问题；
- `info`：盘点信息或改进机会。

置信度单独标为高、中、低。低置信度项目通常应作为候选项，不能作为阻断问题。

详细冲突分类和黄金样例属于下一阶段，可以细化这些定义，但不能改变上述产品原则。

## 12. 产品级验收标准

### 12.1 范围与确定性正确性

- AC-1：在获批黄金样例中，产品盘点出 100% 受支持且范围内的来源，并报告所有有意
  排除的来源；
- AC-2：P0 确定性规则在获批黄金集上达到至少 95% 精确率和 95% 召回率，且不存在
  critical 漏报；
- AC-3：100% 的问题都包含规则标识、严重程度、置信度或确定性状态、来源位置、证据
  和下一步建议；
- AC-4：同一底层结果生成的终端、Markdown 和 JSON 输出在语义上保持一致。

### 12.2 语义实用性

- AC-5：在获批语义黄金集上，阻断级语义问题的精确率至少为 90%；全部语义问题的
  精确率至少为 85%，召回率至少为 75%；
- AC-6：评审者认为至少 80% 的语义问题可以采取行动；所有刻意设置的模糊案例都不能
  被强行归入 `pass` 或 `finding`；
- AC-7：人工报告和 JSON 都能区分冲突、重复、互补、覆盖和证据不足。

以上是产品目标。阶段 02 定义分类法与黄金样例；阶段 04 定义正式测量方法和发布门禁。

### 12.3 授权与改动安全

- AC-8：所有无有效授权的负向场景中，修改文件数必须为零；
- AC-9：每次写入都在应用前展示精确变更集，包括预授权场景；
- AC-10：有效授权不能在目标、操作、会话或有效期之外复用；
- AC-11：对每一种受支持修复，只要没有并发修改，回退都能恢复精确的先前状态；
- AC-12：如果目标在方案生成后或应用后发生变化，Agent Doctor 必须检测冲突，并在
  应用或回退时避免覆盖无关修改；
- AC-13：已应用、部分应用、被拒绝、失败和已回退状态在变更记录中必须明确且可归因。

### 12.4 隐私与降级模式

- AC-14：网络不可用时，所有 P0 确定性检查仍可完成；
- AC-15：只有语义覆盖已启用、已披露可提交内容范围且用户确认该精确 manifest digest
  时，才能向模型发送内容；
- AC-16：秘密测试数据和未获批脚本内容不得出现在模型请求、报告或变更记录中；
- AC-17：模型分析不可用时，确定性结果仍然可用，语义检查标为 `not_run`。

## 13. 成功指标

达到以下结果即可证明 MVP 成功：

- 高级用户能够发现至少一个真实配置问题，或者有充分理由确认某个怀疑缺少证据；
- Skill 作者能够在本地和 CI 中复现问题；
- 用户不需要相信不透明分数，也能解释阻断问题为什么成立；
- 试用过程中没有任何一次写入缺少有效授权；
- 所有受支持的试用修复都可审阅并可安全回退；
- 至少 80% 的试用用户认为报告比手动审阅同一批配置文件更有用。

使用量、付费转化和企业管理能力不属于 MVP 成功指标。

## 14. 风险与产品应对

| 风险 | 产品应对 |
| --- | --- |
| 语义误报损害信任 | 精确率优先、候选状态、拒绝判断和证据要求 |
| 用户把静态分析误解为运行时事实 | 分开标注观察、推断和未经运行时验证的结论 |
| 修复能力造成权限扩大 | 默认只读、边界授权、精确预览和可撤销 |
| 回退覆盖用户后续工作 | 保存先前状态、检测并发修改、无法安全回退时拒绝执行 |
| 模型使用泄露敏感内容 | 显式且有边界的语义操作、与单次运行精确绑定的披露授权、数据最小化和默认排除 |
| 与安全扫描器同质化 | 明确聚焦配置协调与交互诊断 |
| Codex 行为变化 | 对问题、规则、输入和平台行为假设进行版本化 |
| 过早支持多平台导致质量下降 | 先验证 Codex-first 分类法和评测集，再增加适配器 |

## 16. 已确认的产品决策

## 17. 资料依据

  <https://learn.chatgpt.com/docs/codex-sdk>。
